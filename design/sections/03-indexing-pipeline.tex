\section{Indexing Pipeline}
\label{sec:indexing-pipeline}

The indexing pipeline transforms a directory tree of source files into the
symbol graph stored in SQLite~\cite{brunsfeld2018treesitter}. It runs in five
stages organized into two phases: a structural phase that builds the symbol
graph and a deferred FTS phase that populates the content index.

\subsection{File discovery}

The pipeline begins by enumerating candidate files. When the workspace root
contains a \texttt{.git} directory, codetopo prefers \texttt{git ls-files} to
enumerate tracked files; this automatically respects \texttt{.gitignore} rules
and avoids scanning build artifacts. When no Git repository is detected, the
pipeline falls back to a recursive directory walk using the embedded
\texttt{.gitignore}-aware walker. Files are filtered by extension against the
registered set of language grammars.

Each candidate file is checked against its stored \texttt{mtime} and xxHash
fingerprint. If both match the stored values, the file is skipped entirely
(no parse, no write). This incremental check is the primary source of
startup-time savings on large repositories.

\subsection{Supported languages}

The following 13 languages are supported via tree-sitter grammars and
language-specific extractors: C, C++, C\#, TypeScript, JavaScript, Python,
Rust, Java, Go, Bash, SQL, YAML, and Lua.\footnote{Simon's architecture
summary lists 12; Lua is tracked as experimental.}

\subsection{Parsing}

Accepted files are parsed with the tree-sitter grammar for their detected
language (\texttt{src/index/parser.h:30--101}). Tree-sitter produces a
concrete syntax tree (CST) in memory. Parse errors are tolerated:
tree-sitter performs error-recovery and returns partial trees for files with
syntax errors. The CST is the input to the extractor, and
Figure~\ref{fig:cst-fragment} shows the kind of fragment the extractor walks.

\subsection{Symbol and edge extraction}

The extractor (\texttt{src/index/extractor.cpp:207--297}) walks the CST using
an \emph{iterative stack-based DFS} rather than recursion. This avoids stack
overflow on deeply nested ASTs (e.g., generated files with thousands of nested
expressions). Figure~\ref{fig:extractor-stack} sketches the live work stack
during that traversal.

For each traversed node the extractor identifies:
\begin{itemize}
  \item \textbf{Symbol definitions}: functions, methods, classes, structs,
        enums, type aliases, variables, and constants. Each definition
        produces a \texttt{nodes} row with kind, name, qualified name,
        signature, source span, visibility, and optional docstring.
  \item \textbf{Call expressions}: recorded as \texttt{edges} of kind
        \texttt{calls}. Where the callee can be resolved to a known symbol
        in the current or previously indexed root, the edge carries both
        \texttt{src\_id} and \texttt{dst\_id}; unresolved calls carry
        \texttt{dst\_name} only and are flagged as approximate. A confidence
        floor of 0.3 is applied: edges below that threshold are
        discarded.\footnote{The 0.3 threshold eliminates near-zero-confidence
        guesses (e.g.\ an unqualified \texttt{foo()} that matches dozens of
        candidates) while retaining low-but-plausible edges. Unresolved calls
        stored with only \texttt{dst\_name} are recorded at a default confidence
        of 1.0 and bypass the filter entirely.}
  \item \textbf{References}: import/include, inheritance, field access, and
        type references are recorded in the \texttt{refs} table.
\end{itemize}

\subsection{Persistence}
\label{sec:persistence}

Extracted symbols, edges, and references are written to SQLite in
\emph{batched inserts} (\texttt{src/index/persister.h:117--380}):
\begin{itemize}
  \item Symbol (node) batch size: 100 rows per statement.
  \item Reference batch size: 80 rows per statement.
  \item Edge batch size: 150 rows per statement.\footnote{These batch
        sizes (100 symbols, 80 refs, 150 edges) were tuned empirically against
        SQLite's per-statement bound-value limit of 999. A node row binds
        $\approx$10 columns, so 100 nodes uses $\approx$1000 bindings --- at
        the ceiling. Edge and ref rows bind fewer columns, allowing larger
        batches before the limit is reached.}
\end{itemize}

Before inserting, existing rows for the file are deleted
(\texttt{DELETE WHERE file\_id = ?}), so the operation is idempotent. The
entire insert sequence for one file runs inside a single transaction.

\paragraph{Statement binding and memory efficiency.} Statement parameter binding
is implemented in C++26 using pack indexing (\texttt{src/db/bind.h}), allowing
variadic tuples of heterogeneous SQLite values to be bound directly to 1-based
statement indices (\texttt{args...[Is]}) without recursive template
expansions or intermediate tuple allocations. Memory allocations during
Tree-sitter AST traversals are serviced by a dedicated bump-pointer
\texttt{Arena} pool (\texttt{src/core/arena.h}) that avoids general-purpose
heap contention across parallel worker threads. Furthermore, bounded hot-path
collections adopt C++26 \texttt{std::inplace\_vector<T, N>}
(\texttt{src/core/inplace\_vector.h}) with zero-heap inline storage: child
process execution argument lists (\texttt{N=64}), declaration modifier tokens
(\texttt{N=16}), argument classification patterns (\texttt{N=16}), and search
query term splitting (\texttt{N=8}).

\paragraph{Bulk mode.} When the initial index covers more than 1\,000 files,
the pipeline enters \emph{bulk mode}: it drops secondary indexes and FTS
triggers before the load and rebuilds them afterwards. This avoids repeated
B-tree rebalancing during the insert flood and significantly reduces total
indexing time on large repositories.

\subsection{Structural centrality and PageRank}
\label{sec:pagerank}

Following cross-file reference resolution, the pipeline performs a graph-wide
centrality calculation (\texttt{src/index/pagerank.h}) to quantify architectural
importance:

\begin{equation}
  PR^{(k+1)}(v) = \frac{1 - d}{N} + \frac{d \cdot S_{\text{dangle}}}{N} + d \sum_{u \in M(v)} \frac{PR^{(k)}(u) \cdot w(u, v)}{W_{\text{out}}(u)}
\end{equation}

where directed edges include \texttt{calls}, \texttt{inherits}, and
\texttt{references} ($w(u,v) \ge 0.1$), $d = 0.85$, and $S_{\text{dangle}}$
redistributes probability mass from sink nodes lacking outgoing edges. Power
iteration terminates when $\Delta < 10^{-5}$ (typically 12--18 iterations,
taking under 15\,ms for 100\,000 edges). Ranks are normalized against the
maximum score ($PR(v) / \max PR \in (0.0, 1.0]$) and persisted into
\texttt{nodes.rank} via a temporary staging table in a single atomic update.

\subsection{FTS rebuild (phase 2)}

After the structural commit (nodes, edges, refs) is finalized, the pipeline
runs a second phase that populates \texttt{content\_fts}. This table is a
\emph{contentless} FTS5 trigram index over source lines
(\S\ref{sec:data-model}). Because it is contentless, rows cannot be copied
from another database; they must be inserted by reading source files from
disk line-by-line. Deferring this phase means the write lock is held for only
as long as the structural data requires.

While cold-start indexing constructs the graph across the entire repository in hundreds
or thousands of seconds for large software systems (\S\ref{sec:status}), interactive developer
workflows demand latency on the order of tens to hundreds of milliseconds. Full graph reconstruction
on each file save is computationally infeasible. codetopo therefore implements an incremental
re-indexing pipeline founded on two-tier change detection~\cite{ryder1988incremental} and
targeted symbol attraction.

\paragraph{Two-tier change detection.} The change detection engine (\texttt{src/\allowbreak index/\allowbreak change\_detector.h})
identifies filesystem changes without reading unnecessary file bodies into memory:
\begin{enumerate}
  \item \textbf{Tier 1: Metadata fast path ($O(1)$ stat).} Each discovered file's filesystem metadata
        --- specifically modification timestamp in nanoseconds (\texttt{mtime\_ns}) and size in bytes
        (\texttt{size\_bytes}) --- is compared directly against the corresponding row in SQLite's
        \texttt{files} table. If both values match the stored record, the file is classified as
        unmodified, completely bypassing disk I/O and syntax parsing.
  \item \textbf{Tier 2: Content fingerprint verification (xxHash64).} When either \texttt{mtime\_ns} or
        \texttt{size\_bytes} differs (e.g., an editor timestamp update, a file touch, or formatting pass),
        codetopo reads the file and computes a 64-bit non-cryptographic xxHash fingerprint. If the newly
        computed digest matches \texttt{files.content\_hash}, the file's semantic content is identical;
        the stored metadata is updated in SQLite, and parsing is skipped.
\end{enumerate}
The detector partitions the workspace into four disjoint sets: $\mathcal{F}_{\text{new}}$,
$\mathcal{F}_{\text{changed}}$, $\mathcal{F}_{\text{deleted}}$, and $\mathcal{F}_{\text{unchanged}}$.

\paragraph{Targeted persistence and atomic cascades.} For each file in $\mathcal{F}_{\text{changed}}$
or $\mathcal{F}_{\text{deleted}}$, codetopo executes an atomic deletion in SQLite:
\begin{lstlisting}[language=sql]
DELETE FROM files WHERE path = ?;
\end{lstlisting}
Because foreign keys are enforced (\texttt{PRAGMA foreign\_keys = ON}), this single deletion triggers
cascading drops across all related tables:
\begin{itemize}
  \item In \texttt{nodes}: all symbol and file nodes belonging to \texttt{file\_id} are removed.
  \item In \texttt{edges}: all directed edges with matching \texttt{file\_id}, \texttt{src\_id}, or
        \texttt{dst\_id} are deleted.
  \item In \texttt{refs} and \texttt{content\_fts\_tracker}: fine-grained reference sites and FTS tracking
        entries for that file are expunged.
\end{itemize}
Files in $\mathcal{F}_{\text{new}}$ and $\mathcal{F}_{\text{changed}}$ are then parsed by tree-sitter,
and their newly extracted nodes, intra-file edges, and references are inserted within a batched
transaction (\S\ref{sec:persistence}).

\paragraph{The symbol attraction mechanism.} A fundamental challenge in incremental graph updating is
cross-file edge resolution:
\begin{enumerate}
  \item \emph{Outgoing calls:} Newly introduced or modified calls within the changed files must be
        resolved against the global symbol table.
  \item \emph{Incoming calls (Attraction):} Unmodified files across the rest of the repository may contain
        previously unresolved call references (\texttt{edges.dst\_id IS NULL} or dangling approximate
        edges) whose target definition was just added or renamed in the modified files.
\end{enumerate}
Scanning millions of existing edges across the entire repository to resolve these incoming calls would
destroy incremental performance. Furthermore, SQLite's cost-based query planner does not collect
distribution statistics (\texttt{ANALYZE}) over temporary tables created during incremental runs;
without intervention, the planner may default to a full table scan over the global \texttt{nodes} or
\texttt{refs} tables.

codetopo resolves this bottleneck through a targeted multi-stage join query driven by temporary
in-memory tables (\texttt{src/index/persister.h:638--735}) with explicit \texttt{CROSS JOIN} ordering:
\begin{itemize}
  \item \texttt{temp.\_\_ct\_changed(path)}: Holds the subset of changed file paths.
  \item \texttt{temp.\_\_ct\_defnames(name)}: Populated via a \texttt{CROSS JOIN} from \texttt{\_\_ct\_changed}
        to \texttt{nodes} indexed on \texttt{idx\_nodes\_file\_id}, collecting only the symbol names defined
        by the newly persisted files.
  \item \texttt{temp.\_\_ct\_kinds(kind)}: Restricts queries to resolvable edge kinds (\texttt{call},
        \texttt{include}, \texttt{inherit}, \texttt{type\_ref}).
  \item \texttt{temp.\_\_ct\_affected(id)}: Collects the exact row IDs of references in \texttt{refs} requiring
        re-resolution by taking the union of: (1)~unresolved references belonging to the changed files themselves,
        and (2)~global unresolved references in unmodified files that match any symbol name defined in
        \texttt{\_\_ct\_defnames}, probed through the composite index \texttt{idx\_refs\_kind\_name}.
  \item \texttt{temp.\_\_ct\_want(name)}: Holds the candidate symbol names and their bare suffixes.
\end{itemize}
By pinning the small temporary tables as the outer driving loops via \texttt{CROSS JOIN}, SQLite is forced
to access \texttt{refs} and \texttt{nodes} via point lookups on their primary keys and covering indexes.
The total incremental resolution complexity is bounded by $O(|\mathcal{D}_{\text{changed}}| \cdot \bar{d})$,
where $|\mathcal{D}_{\text{changed}}|$ is the number of symbol definitions in the changed files and $\bar{d}$
is the average in-degree, executing in milliseconds even in repositories with millions of edges.

\subsection{Filesystem watching and in-flight change coalescing}
\label{sec:watcher-concurrency}

In an active development session, file changes arrive in asynchronous bursts: rapid keystrokes, compiler
artifacts, multi-file code generator executions, or branch checkouts. The watcher subsystem
(\texttt{src/watch/watcher.h}) and MCP server harness (\texttt{src/cli/cmd\_mcp.h}) coordinate live
synchronization through kernel event streaming, debouncing, and in-flight change coalescing.

\paragraph{Native filesystem backends.} Rather than polling the directory tree, codetopo binds to
platform-native kernel event facilities:
\begin{itemize}
  \item \textbf{macOS}: Apple \texttt{FSEvents} framework, providing recursive file monitoring with
        kernel-level stream coalescing and low wake-up overhead.
  \item \textbf{Linux}: \texttt{inotify} directory watches with descriptor multiplexing via \texttt{epoll}.
  \item \textbf{Windows}: \texttt{ReadDirectory\allowbreak ChangesW} serviced via asynchronous I/O completion ports (IOCP).
\end{itemize}

\paragraph{Quiet-window debouncing.} Filesystem events trigger a quiet-window debounce timer
(configurable, defaulting to $1\,000\,\mathrm{ms}$). Successive file write notifications received before the
window expires reset the timer, collapsing intermediate editor saves and batch file emissions into a single
synthesized notification. Internal files under \texttt{.codetopo/} (the active SQLite database, write-ahead
logs, and temporary file lists) and transient \texttt{.git/} internal indices are strictly filtered out
to prevent self-triggering feedback loops.

\paragraph{In-flight change coalescing (\texttt{ReindexState}).} A critical concurrency dilemma arises
when additional files are modified while an incremental re-indexing job is \emph{already actively executing}:
\begin{itemize}
  \item Spawning a concurrent child indexer process against the same SQLite database leads to database write
        lock contention (\texttt{SQLITE\_BUSY}) or process deadlock.
  \item Aborting the running indexer wastes completed tree-sitter parse work and can lead to starvation under
        continuous file saves.
  \item Dropping the incoming event results in permanent graph desynchronization, where the database reflects
        an obsolete file snapshot.
\end{itemize}

codetopo resolves this with an explicit, thread-safe coalescing state machine, encapsulated in
\texttt{ReindexState} (\texttt{src/cli/cmd\_mcp.h:30--145}) and coordinated by a dedicated background
\texttt{monitor\_thread}. Figure~\ref{fig:reindex-coalescing} depicts the state transitions.

The state machine operates under mutual exclusion (\texttt{std::mutex}):
\begin{enumerate}
  \item \textbf{Transition to Active:} When the server is in the \texttt{Idle} state (\texttt{running = false}),
        a debounced watcher event sets \texttt{running = true}, stores the affected paths in
        \texttt{queued\_paths}, and launches \texttt{monitor\_thread}.
  \item \textbf{Coalescing During Execution:} While the child indexer process runs in the background, any newly
        arriving watcher events observe \texttt{running == true}. Under the mutex lock, the event handler
        appends the new relative paths into \texttt{queued\_paths}, flags \texttt{queued = true}, logs the
        deferral, and returns immediately. If an event indicates a repository-wide change (such as a branch switch),
        \texttt{queued\_full = true} is set, clearing individual paths.
  \item \textbf{Serialized Handoff:} When the active child indexer completes its SQLite commit and exits, the
        \texttt{monitor\_thread} re-acquires the mutex. If \texttt{queued == true}, it atomically drains
        \texttt{queued\_paths} into a local buffer, resets \texttt{queued = false}, writes the paths to a unique
        staging file (\texttt{.codetopo/\allowbreak changed-files-\allowbreak\textless timestamp\textgreater-\allowbreak\textless seq\textgreater.lst}),
        and immediately launches a subsequent targeted indexing pass.
  \item \textbf{Return to Idle:} Only when the child completes and no pending events have been queued during its run
        (\texttt{queued == false}) does the monitor set \texttt{running = false} and terminate.
\end{enumerate}
This ensures strict serial transactional execution against the SQLite database with zero dropped notifications and
zero redundant process spawns.

\subsection{Border cases and fault tolerance}
\label{sec:border-cases}

Real-world code editing presents complex edge cases across version control operations, filesystem race conditions,
and concurrent database access. codetopo incorporates systematic defenses for these edge scenarios:

\paragraph{Git branch switching and commit tracking.} A Git branch checkout or fast-forward pull can atomically
modify, add, and delete thousands of files simultaneously. Tracking individual filesystem timestamps during a switch
can overwhelm event queues or trigger false intermediate states.
\begin{itemize}
  \item \textbf{HEAD monitoring:} The watcher explicitly observes \texttt{.git/HEAD} and ref changes. When a
        branch switch is detected, codetopo extracts the new commit SHA and compares it to \texttt{last\_known\_head}
        stored in the \texttt{kv} metadata table.
  \item \textbf{Targeted Git diff reconciliation:} Rather than walking the entire workspace filesystem, codetopo
        executes \texttt{git diff -{}-name-only \textless old\_head\textgreater\ \textless new\_head\textgreater}. The resulting file list is passed directly to
        the targeted re-indexer, restricting parsing exclusively to files modified between the two commits.
  \item \textbf{Automatic fallback:} If Git history was rewritten (e.g., an interactive rebase, squashed commits, or
        a detached HEAD where commit ancestry is severed), or if the diff command fails, codetopo automatically
        escalates to a repository-wide two-tier reconciliation pass (\texttt{queued\_full = true}).
\end{itemize}

\paragraph{File renames and directory moves.} A file rename is surfaced by kernel watchers as an asynchronous pair
of delete and create events. codetopo guarantees consistency regardless of event order:
\begin{enumerate}
  \item Deletion of the old path triggers SQLite's foreign key cascade (\texttt{ON DELETE CASCADE}), removing the
        old \texttt{files} row and purging its associated nodes, edges, and FTS tokens.
  \item Creation of the new path inserts the new file and parses its definitions.
  \item The symbol attraction probe (\texttt{\_\_ct\_defnames}) detects the symbols now defined at the new path,
        querying \texttt{idx\_refs\_kind\_name} to automatically re-bind existing call sites across unmodified files
        to the new node IDs.
\end{enumerate}

\paragraph{Partial and syntactically malformed writes.} During rapid editing, language server formatting passes, or
interrupted disk flushes, source files frequently exist in syntactically incomplete states (e.g., unclosed delimiters,
truncated tokens).
\begin{itemize}
  \item Rather than failing or rejecting the file, tree-sitter employs resilient GLR/LR error-recovery parsing,
        constructing concrete syntax trees containing \texttt{ERROR} and \texttt{MISSING} nodes.
  \item The extractor isolates valid symbol declarations and intra-function blocks around the malformed regions,
        marking the database record as \texttt{parse\_status = 'partial'}.
  \item When the editor completes the write, the filesystem mtime changes, the debounce timer elapses, and the
        file is cleanly re-parsed, atomically replacing the partial CST with the valid syntax graph.
\end{itemize}

\paragraph{Concurrent reader-writer isolation (SQLite WAL).} During active re-indexing, AI coding agents and MCP clients
continue issuing high-frequency read queries (\texttt{context\_for}, \texttt{symbol\_search}, \texttt{callers\_approx}).
codetopo configures SQLite in Write-Ahead Logging mode (\texttt{PRAGMA journal\_mode = WAL}):
\begin{itemize}
  \item Writers write new database pages sequentially into the \texttt{-wal} log file without acquiring exclusive
        locks on the main database file.
  \item Readers read concurrently from a fixed snapshot of the database and WAL log, never blocking or being blocked
        by the active indexer.
  \item Upon transaction finalization, the indexer triggers \texttt{server.request\_refresh()}, which advances an internal
        generation counter and purges cached prepared statements in \texttt{QueryCache} (\S\ref{sec:querycache}),
        ensuring subsequent MCP queries immediately observe the committed changes.
\end{itemize}

\paragraph{Multi-process mutual exclusion (\texttt{FileLock}).} A developer may invoke the CLI indexer (\texttt{codetopo index})
in a terminal while an MCP server daemon is concurrently monitoring the same repository in the background.
codetopo enforces mutual exclusion at the operating system level using PID-based file locks (\texttt{src/util/lock.h}):
\begin{itemize}
  \item The writer process creates an exclusive lock file at \texttt{.codetopo/index.sqlite.lock} using atomic system calls
        (\texttt{O\_CREAT | O\_EXCL} on POSIX, \texttt{CREATE\_NEW} on Windows) and records its process identifier (PID).
  \item \textbf{Stale lock detection:} If a preceding indexer process was terminated abruptly (e.g., via \texttt{SIGKILL},
        out-of-memory killer, or power failure) without removing its lock file, subsequent processes inspect the stored PID
        using \texttt{kill(pid, 0)} on Unix or \texttt{OpenProcess} on Windows. If the recorded PID is no longer alive, the
        stale lock is broken automatically, logging a warning and resuming operation without requiring manual cleanup.
  \item \textbf{Cooperative backoff:} If the lock is held by an active live process, secondary indexers block with an exponential
        backoff up to a 30-second timeout before aborting with a descriptive error message indicating the holder PID.
\end{itemize}

\paragraph{Crash resilience and transactional rollback.} If power failure or hardware interruption occurs in the middle
of an incremental pass, SQLite's write-ahead log ensures ACID transactional integrity. Any uncommitted index updates or
partial batches are automatically rolled back upon reopening the database, preventing structural corruptions in B-tree
indices or dangling edges.
